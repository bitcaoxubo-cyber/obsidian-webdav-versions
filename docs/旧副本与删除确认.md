# 旧副本与删除确认：0.4.0-beta.4 交付与复核

基线：`19955ebf3ed0089b893e0ca0a3e70a57b08a096c`（0.4.0-beta.3）。分支：`fix/stale-copies`。

**完整自动测试 358/358 通过。尚未发布，等待复核；本轮只开 PR，不合并、不打 tag、不发布。**

## 1. 摘要

本评审版阻止丢失同步记录的设备重新上传可识别的历史旧副本，并把需要用户决定的删除与冲突集中到一个窗口。两项先行保护是停止手机空目录自动清理，以及在永久删除设置下阻止确认窗口删除文件。完整自动测试 358/358 通过；全部连接设备都需要升级才能获得旧副本保护，真实手机验收尚未完成。

## 2. 逐场景实测结果

最终合并验证 **358/358 通过，失败 0**：原 261 项，加 E0 14 项、E1 25 项、E2 引擎 42 项、E2 界面 14 项及 E3 双平台 2 项。E0、E1 此前分别单独基于 beta.3 完成 275/275、286/286 隔离验证，最终总数不重复计算原测试。

### 2.3 E0：经用户追加授权的两项保护

## 3. 引擎改动

E1 已实现同一路径历史识别；被判定为已删除历史旧副本的文件，只有明确选择保留后才恢复上传。没有新增远端字段或持久化状态字段。实现沿用任务书参考方案的分类原则，并增加提前使用哈希缓存、成功轮次的运行时清单及增量重查规则。

| 本地无绑定文件的情况 | 已实现处理 |
|---|---|
| 本机已确认过该路径的删除，之后重新出现 | 保持 `s.absent` 优先级，按用户有意重建上传 |
| 内容等于同一路径的历史版本，远端已有更新内容 | 绑定到匹配的历史父版本，经原有应用步骤与 CAS 更新到最新内容；不发布旧副本 |
| 内容等于同一路径历史版本，远端当前全为删除叶子 | 留在本机，进入等待确认清单；不上传、不自动删除、不建立绑定 |
| 内容等于远端当前内容 | 直接认领当前版本，不上传 |
| 内容与该路径全部历史版本不同 | 依照原规则上传，真实删除对修改冲突继续保留 |
| 本轮明确 `keep` 且远端当前全为删除叶子 | 以当前全部删除叶子为父版本上传；已有 `s.absent` 的重建规则仍优先 |

`_recognizeUnbound` 只查看 `before.byPath.get(physical)`，不会用其他路径的历史认领文件。对有历史、无绑定的候选，先调用本轮哈希观察；缓存有效时无需读取完整正文。首次扫描、缓存失效或实际上传仍按原规则读取和校验；普通无历史的首次上传保持原有路径与计数。

认领后的下载继续走既有内容校验、CAS 和未保存编辑器检查。E1 的 T12、T13 证明下载期间的新修改及未保存输入没有被认领步骤覆盖。

### 3.1 E1 已确定的接口

| 名称 | 类型及用途 | 生命周期 |
|---|---|---|
| `sync(options).keep` | `Array<string>`；本轮明确要求保留并重新同步的路径 | 每轮转换为 `Set`，不把许可永久保存；与脏路径合并进入本轮检查 |
| `result.stalePaths` | 按路径排序的 `Array<string>` | 当前成功轮次后仍等待确认的旧副本路径；不进入 `deferredPaths` |
| `result.staleCopies` | 按路径排序的 `Array<{ path: string, hash: string, tips: string[] }>` | `hash` 是本地旧副本的内容摘要；`tips` 是观察到的远端删除叶子快照，供 E2 检查确认是否过期；结果中的条目和 `tips` 数组均复制输出 |
| `engine.staleCopies` | 实例内 `Map<path, { path, hash, tips }>` | 仅保留上一成功轮次的等待清单，不写主快照或独立日志 |
| `engine.nextStaleCopies` | 本轮待提交的运行时 `Map` | 全量轮从空表重建；增量轮复制旧表后重查相关路径；同步成功后替换实例清单 |

干净增量轮保留等待清单；本地事件、明确保留选项，或远端该路径叶子变化时重新分类。重启后的首次全量轮可以从本地文件与远端历史重新发现旧副本，不依赖新增状态字段。旧副本本身不代表已经见证删除，等待确认时不会写入 `s.absent`。

E1 以分支中的“E1: 认领同路径历史旧副本并等待删除确认”提交定位。

### 3.2 E2 接口与状态边界

`engine.confirm(actions, callbacks)` 复用引擎串行队列，只执行一轮全量同步。它先读取当前远端视图、校验确认条目，再处理决定，最后执行正常捕获和应用；不会对每个文件各跑一轮同步。

| 接口或字段 | 结构与含义 |
|---|---|
| `actions` | `Array<{ kind, entry, selected? }>`；`kind` 为 `stale-delete`、`stale-keep`、`conflict-delete` 或 `resolve`，`entry` 来自展示时的确认数据 |
| `callbacks.canTrash(physical, hash)` | 回收前预检，返回 `true` 才可继续；检查活动状态、文件内容、文件身份及未保存输入 |
| `callbacks.trash(physical, hash)` | 实际回收入口；插件重新获取并校验删除令牌，检查回收站设置后调用 `app.fileManager.trashFile` |
| `confirmations.staleCopies` | 与 `result.staleCopies` 相同的等待确认数组：`{ path, hash, tips }` |
| `confirmations.deletionConflicts` | `Array<{ path, tips, files, devices, unchanged, selected }>`；`files` 为 `{ physical, hash }[]`，`unchanged` 表示每个存活内容都在某条删除记录的祖先中出现过 |
| `confirmations.staleConflicts` | `Array<{ path, tips, files, devices, selected }>`；两个内容组之间只有单向历史证据时，`selected` 指向较新内容的本地文件；双向证据不进入此组 |
| `appliedDecisions` | 完整处理的逻辑路径数量，不是物理文件回收数 |
| `skippedDecisions` | `Array<{ kind, path, reason }>`；记录未执行或未完整完成的确认动作，无效路径可为 `null` |
| `trashedFiles` | 回收回调明确返回成功的物理文件数量，包括同一路径后来部分跳过前已经回收的文件 |
| `directoryCleanupBlocked` | 本轮候选空目录因缺少可信原子删除能力而保留的布尔标记 |

跳过原因包括 `invalid-entry`、`duplicate`、`remote-changed`、`baseline-changed`、`invalid-selection`、`trash-unavailable`、`local-changed`、`local-or-review-changed`。网络、内容读取、校验回调或回收回调的普通 IO 错误仍抛出；只有专门表示确认过期的 `ConfirmationChanged` 被转换为跳过。

以上结果字段、动作和清单均为运行时数据，不进入持久化状态。`stalePaths`、`staleCopies` 继续保留，供旧副本列表及界面使用。

### 3.3 删除与冲突解决的校验和中断

删除前将展示快照的 `tips` 与本轮当前叶子比较，文件列表及哈希也必须匹配。正文和各冲突副本逐一检查内容与编辑器保护；对于删除冲突，已验证的当前等内容父版本在首次回收前统一保存到检查点，保证回收后、发布删除前中断时仍能正确接续这些父版本。

`_resolve` 保留原有绑定、已审阅叶子、冲突仍存在、其他副本内容未变、选择文件存在等约束。确认入口额外校验选中文件的哈希和编辑器状态；不通过时仅跳过该解决动作，其他有效路径继续处理。

界面的删除令牌捕获同一文件对象、路径、mtime／ctime／size、事件代数和已校验内容；异步校验完成后，在实际回收调用前再次同步检查活动状态、这些标记和未保存输入。回收站设置检查紧邻每次实际 API 调用，永久或不可读取的设置都会阻止删除。

批量不是全有或全无。已有文件成功回收后，另一个文件可能发生变化或失败；已回收数量单独记录并向用户报告，后续变化的副本保留。跳过的是确认动作，普通同步仍可上传用户已经保存的新编辑；不能把“跳过”理解为本轮完全忽略该文件。中断后的正常恢复由既有检查点、绑定和同步日志承担，相关场景见 C8、C11、C12、C14。

## 4. 确认窗口

窗口把可集中处理的三类文件与普通冲突分开显示，删除动作必须由用户明确确认。

| 组别 | 判断与显示 | 按钮行为 |
|---|---|---|
| 本机的旧副本 | 同一路径历史内容相同，远端当前只有删除记录；显示路径 | 删除本机副本，或保留并重新同步；均可批量 |
| 删除冲突 | 同一路径同时存在删除与内容版本；显示路径、保留设备、内容是否与删除前相同 | 内容未变可批量删除；有独立改动只逐个处理；保留沿用冲突解决校验 |
| 旧版本冲突 | 两个内容版本冲突，其中一个与另一个的历史旧内容相同；显示较新文件名 | 逐个或批量采用较新版本 |

普通双方独立修改及待同步文件在下方保留。每个批量按钮先确认数量，一次确认只触发一轮同步；变化或未保存文件跳过并告知数量。完成同步后每轮最多弹一次，只在有新条目时自动弹出；同一次插件加载会话中，关闭后条目不变不重弹，窗口已开时原地更新。这个提示记忆不持久化，重启插件后可能再次提醒。

界面文字示意：

```text
同步确认
  本机的旧副本（N）
    路径       删除本机副本 / 保留并重新同步
    全部删除本机副本 / 全部保留
  删除冲突（N）
    路径、保留设备、内容说明       删除 / 保留
    删除内容未变的 N 个
  旧版本冲突（N）
    路径、较新版本所在文件       采用较新版本
    全部采用较新版本
  其他冲突与待同步文件
```

确认窗口中的“删除”按钮通过 `trashFile` 回收本地文件；“保留”或“采用较新版本”沿用既有 `resolve` 与 CAS 流程收起冗余副本，这些自动收起的副本不承诺进入回收站，原版本仍在远端历史中。永久删除设置由本插件主动阻止，用户改为回收站后可继续；不依赖对 `trashFile` 内部永久删除分支的推断。

## 6. BRAT 的核实结果

已核实 BRAT 的电脑适用性及目标插件文件的覆盖更新方式；本次没有在用户真实库里执行升级。

### 6.1 电脑与手机可使用同一固定版本方式

BRAT 上游 `e9484d8f74b3b75ef59e33c9c9db139abaf039af` 的 manifest 声明 `isDesktopOnly: false`、最低 Obsidian `1.11.4`。结合其通用安装入口，电脑和手机使用同一套添加仓库、选择固定版本流程；固定版本并非手机专用功能。[BRAT manifest](https://github.com/TfTHacker/obsidian42-brat/blob/e9484d8f74b3b75ef59e33c9c9db139abaf039af/manifest.json)

上游开发指南明确说明固定版本会 “Download that exact release version”，并说明可以从 BRAT 插件列表的编辑按钮更改跟踪版本。[固定版本说明](https://github.com/TfTHacker/obsidian42-brat/blob/e9484d8f74b3b75ef59e33c9c9db139abaf039af/BRAT-DEVELOPER-GUIDE.md#L33-L41)、[修改跟踪版本](https://github.com/TfTHacker/obsidian42-brat/blob/e9484d8f74b3b75ef59e33c9c9db139abaf039af/BRAT-DEVELOPER-GUIDE.md#L121-L130)

普通自动更新会跳过已经固定到具体版本的插件，因此用户升级时应编辑固定版本号；不能只点普通更新后假定固定版本已经改变。[固定版本更新规则](https://github.com/TfTHacker/obsidian42-brat/blob/e9484d8f74b3b75ef59e33c9c9db139abaf039af/src/features/BetaPlugins.ts#L561-L564)

### 6.2 更新不会清空目标插件的同步记录

同一上游提交的 `writeReleaseFilesToPluginFolder` 只在目标目录不存在时创建目录，然后写入 `main.js`、`manifest.json` 和存在时的 `styles.css`。它不清空目标插件文件夹，也不删除目标插件的 `data.json` 或 `local-state/`。[写入函数](https://github.com/TfTHacker/obsidian42-brat/blob/e9484d8f74b3b75ef59e33c9c9db139abaf039af/src/features/BetaPlugins.ts#L308-L317)

安装和已有插件更新都使用该写入函数；更新后加载清单并重新加载插件。该结论针对 BRAT 的目标插件更新操作，不等于对第三方插件自身启动行为作保证。[安装调用](https://github.com/TfTHacker/obsidian42-brat/blob/e9484d8f74b3b75ef59e33c9c9db139abaf039af/src/features/BetaPlugins.ts#L508-L518)、[更新调用](https://github.com/TfTHacker/obsidian42-brat/blob/e9484d8f74b3b75ef59e33c9c9db139abaf039af/src/features/BetaPlugins.ts#L601-L604)

用户已经报告手机通过 BRAT 从 beta.1 更新到 beta.3 后同步记录仍在；这是实际使用旁证，电脑适用性和文件覆盖范围的依据仍是以上上游资料。未在本次文档核验中操作真实笔记库。

### 6.3 删除接口的版本依据

官方 `obsidian@1.11.4` 发布包对应 API 提交 `e30998d580abffad28cc9f370d2f4defbfa2081b`。该版本声明 `FileManager.trashFile(TAbstractFile)` 为公开 API，注明自 `1.6.6` 起提供，并说明按用户 trash 偏好处理文件或文件夹；未标记桌面专用。[1.11.4 对应 API 声明](https://github.com/obsidianmd/obsidian-api/blob/e30998d580abffad28cc9f370d2f4defbfa2081b/obsidian.d.ts#L2475-L2482)

该声明不等于真实手机验收，也不证明永久删除设置下的内部实现。本版本不依赖后一项推断，而是在该设置下阻止确认窗口删除。

## 7. 已知限制与未实施项

手机空目录自动清理已停用，真实手机验收仍未完成；不能把自动化模型结果当作平台能力保证。

- 真实手机适配器无法保证原子地只移除空目录。本版保留旧空文件夹，文件删除与移动同步不受此停用影响。
- `next` 最初丢失的原因仍未确认，已有恢复修复不等于已确认真实故障根因。
- 旧副本识别只在新版本设备上生效。运行旧版且没有同步记录的设备仍可能重新上传旧内容，必须更新所有连接设备。
- 普通独立编辑继续保留；等待确认的文件不会自动删除，删除前仍要通过内容、编辑器和设置检查。
- 不改变远端协议，不迁移本地同步记录的存放位置，不新增自动检查更新，不清理远端历史，不新增后台同步。
- 本次不写真实 WebDAV，不修改既有 beta.1、beta.2、beta.3 Release 附件；历史性能证据保持原样。
- Obsidian 删除接口或 `vault.getConfig` 不可用、设置读取失败或返回未知值时，确认删除会被拒绝；不会改用直接删除兜底。最低版本公开 API 可用性不等于所有真机环境的设置读取能力已经验收。
- 批量处理可能部分成功；界面同时报告实际回收数和跳过数。普通同步仍处理已保存的新编辑，原有冲突解决对冗余副本的收起不等于移入回收站。
- 关闭后不重复提示只覆盖本次插件加载会话，重启后可以再次提醒。
- 三条无延迟基准完全一致；延迟场景存在已授权范围内的检查点字节波动，明细见第 2.5 节。

## 8. 给用户的清理步骤

先保留每台设备的内容和记录，更新全部设备，再用确认窗口处理已经“删掉又回来”的文件。

1. 备份所有设备的本地库，暂停自动同步；不要卸载插件或删除 `local-state/`。
2. 本评审版复核并正式发布后，用 BRAT 编辑固定版本，或关闭 Obsidian 后覆盖 `main.js`、`manifest.json`。保留 `data.json`、`local-state/` 和笔记；先把所有连接设备都升级。
3. 在一台设备保持前台，手动“立即同步”，打开统一确认窗口。
4. 检查“本机的旧副本”，选择删除不需要的本机旧文件，或保留并重新同步。
5. 在“删除冲突”中核对路径和设备；需要清理的、内容未变的文件可用批量删除。删除后有改动的文件先逐个比较，不在批量删除中处理。
6. 在“旧版本冲突”中核对较新版本，按需采用；普通独立修改继续手工比较、合并。
7. 删除设置若为“永久删除”，先改成系统回收站或 Obsidian 回收站，再继续。批量确认前检查数量；被跳过的文件按提示重新比较。
8. 依次在其他设备同步，确认保留的内容、删除结果和冲突状态符合预期，再恢复自动同步。手机旧空文件夹可能继续保留；需要整理时自行检查后处理。

当前交付为 `fix/stale-copies` 评审分支，以第 2.4 节的任务提交主题定位；正式 PR 链接由交付回复和 PR 描述提供。本版本尚未发布，以上正式升级步骤仅在复核及发布后执行。
