## 为什么必须停下

任务书第 7 节要求遇到以下情况先停下来说明、不得自行决定：

> 发现附录模型的结果在基线上复现不出来。

原附录场景 4 和 H9 要求，新版本到达时外部工具刚改了同一篇，`vault/` 的原路径仍是外部工具的内容。实际在**未修改的 `bdb26b7`** 上，原脚本重复 12 次，6 次原 `a.md` 是外部工具内容，6 次原路径变为 Mac 内容。根代理额外独立重跑的第一轮也得到 Mac 内容。新增集成测试同样遇到一次失败、单独重跑又通过。

因此这是基线行为与验收假设不一致，不能以一次通过、重试直到变绿或放宽断言来认定 H9 通过。

## 证据

- 任务书附录原模型原样提取，未改模型逻辑。按任务书要求在仓库外空目录运行，并把未修改基线目录作为参数；模型仅使用内存假远端与临时磁盘。
- [12 次基线输出摘要](headless-evidence/h9-baseline-12-trials.json)：每次进程退出均为 0，但场景 4 的原路径内容不同。
- [独立失败轮完整输出](headless-evidence/h9-baseline-failure.txt)：第 4 场景输出 `a.md on NAS = "a edited again on Mac"`。
- `test/headless-integration.test.js` 的 `H7/H8/H9` 测试保留原要求，未改成宽松判断；当前因此存在不稳定失败。

复现方式（不连接真实 WebDAV）：

```sh
# 将任务书附录脚本一原样保存为仓库外空测试目录中的 appendix-model.js。
# baseline 是 git archive bdb26b7 解出的只读代码快照。
node appendix-model.js /path/to/baseline
```

重复运行并观察第 4 场景；不要只检查进程退出码，因为原模型仅打印结果，没有 H9 断言。

## 原因

`src/protocol.js` 的 `makeRevision` 默认使用随机 UUID 作为 nonce（第 64 行），版本 ID 对含 nonce 的内容做摘要（第 35–36 行）。`project` 对同一路径的叶版本 ID 排序（第 155 行），第一个不同正文占据原路径，其余正文使用冲突副本名称（第 159–162 行）。

`src/engine.js` 先捕获同步前已存在的本地编辑，再按包含新分支的投影应用文件（第 915–917 行）。所以两个版本会保留，但由哪一个版本占原路径并非按“来自外部工具”决定。真正发生于扫描之后、引擎尚未观察到的修改另有 compare-and-set 保护；不能换成这个不同的时序来声称原附录场景已经通过。

上述两个源文件与基线无差异，均属于任务书禁改范围。
